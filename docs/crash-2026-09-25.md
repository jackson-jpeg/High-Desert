# VPS lockup and reboot — 2026-09-24

The file is named for the recovery mandate that asked for it; the lockup itself
was **2026-09-24 16:36:11Z**. All times UTC. Everything below was measured on
the box after the reboot, not recalled.

## What was running

- High Desert `1779606`, the sampler and backup timers, Postgres, nginx.
- `openclaw-gateway.service` as a systemd **user** unit under `root`, restarting
  on `Cannot find module '/usr/lib/node_modules/openclaw/dist/index.js'` — 72,151
  journal lines on the previous boot and still going at 16:36:10. The
  system-level OpenClaw had been retired; this copy survived it.
- Parallel Claude Code sessions (other projects).

## What the journal shows about the lockup

- **No disk errors**: nothing from ext4, `blk_update_request`, or I/O errors on
  either boot. Root mounted cleanly on the way back up.
- **No hung-task, soft-lockup or RCU-stall** messages in the 661 kernel
  warning-or-worse lines since 12:00.
- **One OOM**, `sanger-next` at 12:33 — four hours before the lockup, so not it.
- The journal ends mid-stream with no kernel message at all. That is consistent
  with the hypervisor stopping or resetting the guest, and not consistent with a
  guest-side panic, which would normally leave a trace. The cause was cleared
  outside this repo; this document records the evidence, not a verdict.

  branch is already in `main`. `self-host` carries one commit not in `main`
  (`dd38149`, 2026-07-27), old and already on origin. `/root/.hd-deploy-stage`

## What came back on its own

Every unit came up at boot, enabled rather than merely started:
`highdesert`, `nginx`, `postgresql` (which pulls in `postgresql@16-main` —
hence that one's `enabled-runtime`), `highdesert-sample.timer`,
`highdesert-backup.timer`. `systemctl --failed` was empty. No redeploy was
needed: live was already `1779606`.

## State after recovery (20:50Z)

- `/`, `/library`, `/radio`, `/stats` all 200 in ~22 ms; 8 online, 3 listening.
- `highdesert-status`: all eight lines OK, exit 0.
- **Steal: fixed by the reboot.** 1.6–5% in every 10-minute sample since
  16:50 (the 38.6% at 16:50 covers boot itself), 2.4% live. Idle 75–94%.
- Disk: `/` and `/var` share `sda1`, 64% used, 35 GB free.

## If it happens again

- `vps-cpu-alert.timer` emails on steal above 30% over 30 minutes, so a
  recurring clamp is no longer silent.
- `atop -r /var/log/atop/atop_YYYYMMDD` has per-process history; before this
  incident, the Sep 22 load left no per-process record at all.
- Check user units as well as system ones — `systemctl --user list-units
  --all` — the process that outlived its retirement here was a user unit.
